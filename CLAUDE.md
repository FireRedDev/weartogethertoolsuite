# CLAUDE.md — Wear Together Order Suite

Orientierung für Code-Änderungen. Für tiefe Details der Report-Logik: `AGENTIC_INTENT_SPEC.md`. Nutzer-Doku: `README.md`, Änderungen: `CHANGELOG.md`.

## Was das ist
Laravel-13-App (PHP ≥ 8.3, SQLite), Web-Nachfolger einer Python/Tkinter-Toolsuite. Direkt im Repo-Root (kein Unterordner) wegen RunCloud Atomic Deployment. Deutschsprachige UI. CSS/JS inline in Blade-Views (kein Node-Build). Login per gemeinsamem `TOOL_PASSWORD` (Middleware `ToolAuth`; leer = kein Login).

Fünf Module, verlinkt von der Startseite (`/` → `HomeController`):
1. **Auftragsdokumente** (`/auftragsdokumente`, `tool.*`/`shop.*`/`job.*`) — Bestell-Export → 3 Excel-Reports + Verteil-PDF. Kern-Logik in `app/Services/*` (nicht `SchoolShop/`). **Zellgenau identisch zum Legacy-Python-Tool — abgesichert durch Golden-File-Tests (`tests/Feature/GoldenFileTest.php`). Diese Logik/Defaults (`config/ordersuite.php`) NICHT verändern, ohne die Golden-Files bewusst neu zu erzeugen.**
2. **Schul-Onboarding** (`/schulen`, `schools.*`) — FluentForms-Webhook → Konfigurator → Shop-Anlage (WooCommerce + Pods-CPT „schule" + optional Printify).
3. **Bestellfenster schließen** (`/bestellfenster-schliessen`, `close-window.*`) — Produkte einer Schule auf privat setzen + CPT „Bestellfenster offen" = NEIN.
4. **Auftragsbilanz** (`/auftragsbilanz`, `balance.*`) — die gepflegte Auftragsliste, Nachfolgerin der Excel `Auftragsbilanz_gesamt.xlsx`. **Nur Eingabe und Anzeige, keine Auswertung.** Kern in `app/Services/Balance/`, siehe unten.
5. **Statistiken** (`/statistiken`, `statistics.*`) — Umsatzauswertung nach Schuljahr mit Vorjahresvergleich, Ranglisten, Prognose und den Wirtschaftlichkeitszahlen aus der Auftragsbilanz. Kern in `app/Services/Statistics/`, siehe unten.

Dazu im Schul-Antrag ein **Präsentationsblatt** (A4-PDF je Bestellfenster, siehe unten) und ein Diagnose-Bereich **Admin-Informationen** (`/admin-informationen`, `admin.*`) — Live-Status aller API-Anbindungen, siehe unten.

## Befehle
```bash
php artisan test                 # gesamte Suite (muss vor jedem Push grün sein)
php artisan test --filter=XyzTest
php artisan serve                # lokal; Background-Runs über die Task-Mechanik, nicht `&`
php artisan printify:check --blueprints=JH001   # Printify: Shops/Blueprints/Provider nachschlagen
php artisan printify:check --providers=92
php artisan printify:check --description=92,91  # Blueprint-Katalogbeschreibung (für printify_description in config/schoolshop.php)
php artisan windows:extend --dry-run            # fällige Fenster-Nachfristen anzeigen (Cron: täglich ohne --dry-run)
php artisan backup:create                       # Datenbank + Uploads sichern (Cron: nächtlich)
php artisan sheet:background export.png         # Grafiker-Export -> Hintergrund des Präsentationsblatts
php artisan statistics:warm --runs=20           # Statistik-Daten vorab laden (Cron: nächtlich, optional)
php artisan auftragsbilanz:import --dry-run     # Altdaten erneut übernehmen (beim Deploy läuft das als Migration)
php artisan auftragsbilanz:sync                 # Online-Einnahmen aus dem Shop nachtragen (Cron: nächtlich)
php artisan auftragsbilanz:abgleich --schulen   # Eintrag gegen Shop halten (Konsole, darf nachladen)
```

Die Blade-Vorlage `presentation-sheet/sheet.blade.php` enthält bewusst keinerlei Rechnerei. `shopUrl()` nimmt den echten Kategorie-Slug (`woo_category_slug`, beim Anlegen mitgeschrieben); die Ableitung aus dem Schulnamen ist nur die Rückfallebene für Altbestand.

- **`app/Services/Balance/`** — Modul 4 (Auftragsbilanz):
  - Model `BalanceOrder` (Tabelle `balance_orders`) — eine Zeile je Auftrag, Spalten wie in der Excel. Eingetragen werden nur `revenue_online`, `revenue_cash`, `commission`, `expenses`, `vat` und die Stückzahlen; `revenueTotal()`, `revenueNet()`, `profit()`, `marginShare()` und `productCount()` **rechnen** — in der Excel waren das Formeln, und gespeichert könnten sie nicht mehr zu ihren Teilen passen. `revenueOutsideShop()` ist der Betrag, den der Webshop NICHT kennt.
  - `BalanceReport` — alle Auswertungen (Jahresbilanz, je Schule, je Auftrag, Produkte je Schuljahr, Monatsverlauf der Umsätze außerhalb des Shops). **Rein aus der Datenbank, kein einziger API-Aufruf** — die Auftragsbilanz muss auch bedienbar sein, wenn der Shop klemmt.
  - `ShopComparison` — stellt je Schuljahr den Shop-Wert dem eingetragenen Online-Wert gegenüber (Kasten oben im Modul). Liest nur bereits geladene Monate; fehlt etwas, meldet sie `available = false`.
  - `OnlineRevenueSync` — trägt die Online-Einnahmen verknüpfter Aufträge aus dem Shop nach (`revenue_online` aus dem Fensterumsatz desselben Antrags, also exakt die Zahl des Statistikmoduls). Läuft gedrosselt über `app()->terminating()` und über `php artisan auftragsbilanz:sync`.
  - `AuftragsbilanzImporter` — Altdaten aus `database/data/auftragsbilanz.json` (384 Aufträge, eingefrorener Stand der Excel vom 08.07.2026). Idempotent über Nummer + Schulname + Schuljahr; bestehende Zeilen bleiben unangetastet, außer man verlangt `overwrite`. Aufgerufen von der **Migration** `2026_09_04_091000_import_auftragsbilanz_altdaten` (damit beim Deploy nichts von Hand nachzuholen ist) und von `php artisan auftragsbilanz:import`. In Tests abgeschaltet (`AUFTRAGSBILANZ_IMPORT_ON_MIGRATE=false` in `phpunit.xml`) — sonst lägen 384 fremde Aufträge in jedem Test.
  - `AbgleichAuftragsbilanz` (`php artisan auftragsbilanz:abgleich`) — die einmalige Kontrolle: Eintrag gegen Shop, je Schuljahr, optional je Schule (`--schulen`). **Darf als einziger Weg fehlende Monate nachladen**, weil er auf der Konsole läuft und niemanden warten lässt.
  - Katalog & Defaults: `config/auftragsbilanz.php` (Produktarten, USt.-Satz, `shop_online_from_year`, Schwellen für den Abweichungshinweis).
- **`app/Services/Statistics/`** — Modul 5:
  - `SchoolYear` — Wertobjekt für das Schuljahr (fester Stichtag **1.8. bis 31.7.**, **Sommerferien zählen ans ablaufende Jahr**). `months()` liefert das 12er-Raster ab August, `elapsedShare()`, `isComplete()`, `recent()`.
  - `OrderRepository` — **monatsweiser** Abruf mit eigenem Cache je Kalendermonat (vergangene 24 h, laufender 30 min) und Zeitbudget je Seitenaufruf; nie je Schule abfragen und nie ein ganzes Jahr am Stück (siehe Gotchas). Normalisiert auf Datum + Positionen (Produkt, Menge, Umsatz, Farbe). Der Zeitraum greift um `fetchPadding()` Tage über den Jahresrand hinaus, weil Fenster über den Jahreswechsel reichen können. `orders()` liefert `{orders, complete, loaded, total}` — `complete = false` heißt „Budget aufgebraucht, Rest beim nächsten Aufruf".
  - `ProductGrouper` — fasst Bestellpositionen zu **Produktarten** zusammen (Suchbegriffe aus `schoolshop.catalog` name_suffix + `statistics.product_group_aliases`, längster Treffer gewinnt). Nie nach Produktnamen gruppieren: im Shop heißt jedes Produkt anders, weil der Schulname darin steckt.
  - `RevenueReport` — die Auswertung. **Zwei Zuordnungen laufen nebeneinander:** nach Schuljahr (Bestelldatum → Gesamtumsatz, Monate, Ranglisten, Ø je Bestellung) und nach Bestellfenster (Position → Fenster der Schule → Ø je Fenster; ein Fenster gehört zu dem Schuljahr, in dem es *endet*). Zuordnung Position→Schule läuft über Produkt→Kategorie→`woo_category_id`.
  - `RevenueForecast` — Hochrechnung über den gemittelten **Saisonverlauf** der Vorjahre (nicht linear!), plus Zielumsatz (Standard = Vorjahresumsatz).
  - `StatisticsWarmer` — baut den Datenbestand auf. `progress()` ist eine reine Zwischenspeicher-Abfrage (nie ein Shop-Aufruf), `warm()` holt fehlende Monate mit Sperre + Pause. Angestoßen wird er **nur** über `app()->terminating()` bzw. `php artisan statistics:warm`.
  - `StatisticsFilters` — Filter aus der Adresszeile (Schuljahr, Lieferart, Schule, Puffer, Status, **Quellenschalter** `shop`/`sonstige`), damit die Seite als Lesezeichen taugt. **Das Saisonziel gehört bewusst NICHT hierher.**
  - `SeasonPlan` — die Planungsrechnung: was bis zum Ziel noch offen ist, und wie viele Bestellfenster es dafür je Art noch braucht. Der Ø je Fenster kommt aus den **abgeschlossenen** Fenstern der laufenden Saison UND des Vorjahres (gewichtet nach Anzahl); laufende Fenster zählen nicht mit, sie hätten naturgemäß weniger Umsatz.
  - `Charts/{ColumnChart,BarChart,LineChart,Shapes,Palette}` — Geometrie in PHP, die Blade-Komponenten `<x-chart.columns|bars|lines>` zeichnen nur.
- **`app/Services/IntegrationStatusChecker`** — prüft live alle API-Clients (`testConnection()`-Methode je Client) + `WordPressAdminNotifier` (E-Mail-Alarm **nur** über einen WordPress-REST-Endpunkt, siehe Gotchas). Model `IntegrationStatus` speichert den letzten Stand pro Schnittstelle (verhindert Mehrfach-Benachrichtigung).

## Wichtige Gotchas (teuer erkauft — bitte beachten)
- **Online-Umsatz darf genau EINMAL gezählt werden.** Die Statistik hat zwei Quellen: die Shop-Bestellungen aus WooCommerce und die Auftragsbilanz. Ein Auftrag mit `online_source = 'shop'` steuert deshalb NUR seinen Bargeldanteil bei (`BalanceOrder::revenueOutsideShop()`). Wer das aufweicht — etwa indem er in der Statistik `revenue_online` addiert — verdoppelt den halben Jahresumsatz, und zwar lautlos: Die Zahl sieht plausibel aus, sie ist nur doppelt so hoch.
- **`shop_online_from_year` ist die heikelste Einstellung im Haus — aber sie wirkt NUR beim Import.** Zur Laufzeit entscheidet ausschließlich das Feld `online_source` JE AUFTRAG, ob die Statistik den eingetragenen Online-Betrag verwendet (`manual`) oder ihn aus WooCommerce holt (`shop`). Die Jahreszahl ist die Vorgabe, mit der `AuftragsbilanzImporter` dieses Feld bei den Altdaten gesetzt hat, sonst nichts (`grep shop_online_from_year app/` zeigt genau zwei Verwendungen: Importer und Abgleichbefehl). **Erklärtexte in der UI dürfen daraus keine Regel machen** — „ab Schuljahr X gilt der Shop" ist falsch, sobald jemand einen Auftrag von Hand anders einstellt. Für den Import selbst bleibt die Linie heikel: zu früh gesetzt und ohne Shop-Daten fehlt der Umsatz **vollständig und ohne Fehlermeldung** (bei den Altdaten rund 514.000 €), zu spät zählt er doppelt. Nach jeder Änderung `php artisan auftragsbilanz:abgleich` laufen lassen; die Spalte „Shop meldet" in der Schuljahresbilanz zeigt dasselbe für die geladenen Jahre.
- **Erklärtexte veralten leise.** Sie brechen nichts, sie sagen irgendwann nur etwas Falsches — und niemand merkt es, weil kein Test darauf zeigt. Wer eine Regel ändert, muss die Texte mitziehen; `BedienbarkeitTest` hält die Aussagen fest, die schon einmal an der Wirklichkeit vorbeigingen (Zielvorschlag ohne alle Quellen, „aus dem Webshop" bei abgeschalteter Shop-Quelle, die Jahreszahl als vermeintliche Regel).
- **Der Stichtag des Schuljahres ist 1.8., nicht 1.9.** Er steht in `config('statistics.school_year')` und gilt für BEIDE Module — so rechnen die Jahresbilanzen des Hauses („Bruttoumsatz 1. August bis 31. Juli"). Wer ihn ändert, verschiebt jede historische Zahl; die Monatsdaten im Cache tragen den Stichtag nicht im Schlüssel, also danach einmal „Daten neu laden" anstoßen.
- **Die Umsatzsteuer steht je Auftrag in der Zeile, sie wird nicht global gerechnet.** Vor der GmbH-Gründung (bis in die Saison 2020/21 hinein) fiel keine an — dort steht 0,00 €, und nur dadurch stimmen die alten Zeilen weiter mit der Excel überein. Ein leeres Feld wird beim Speichern aus dem Bruttobetrag hergeleitet (× 20/120), eine ausdrückliche 0 bleibt 0.
- **Die Excel hatte einen Fehler, der in die Altdaten hineinreicht:** Ab Zeile 365 war die Spalte „Schuljahr" als Zahlenreihe fortgeschrieben (`2025-27`, `2025-28`, …). Dadurch wies die Schuljahresbilanz für 2025/26 nur 1.275,84 € statt 48.166,49 € aus. `database/data/auftragsbilanz.json` ist bereits begradigt; `AuftragsbilanzTest` prüft die Jahresverteilung, damit das nicht unbemerkt zurückkommt.
- **Die Auftragsbilanz ruft den Shop nie synchron auf.** `BalanceReport` liest nur die eigene Datenbank, `ShopComparison` und `OnlineRevenueSync` arbeiten mit `startBudget(0.0)` bzw. `allowFetching: false` und tragen erst nach der Antwort nach. Dieselbe Regel wie bei Startseite und Statistik — sie ist zweimal teuer erkauft.
- **Mit ausgeschalteter Shop-Quelle muss die Statistik auch ohne Shop-Zugang laufen.** `StatisticsController` prüft `isConfigured()` nur, wenn `sourceShop` an ist, und überspringt dann Ladeseite und Katalogabruf. Das ist der Ausweg, wenn WooCommerce nicht erreichbar ist — wer die Prüfung wieder bedingungslos macht, nimmt ihn weg.
- **Der Shop-Preis ist BRUTTO, die Printify-Kosten sind NETTO.** Jede Margenrechnung teilt den Verkaufspreis zuerst durch `1 + schoolshop.printify.vat_rate`. Wer das zurückbaut, macht aus jedem Produkt rechnerisch ein besseres Geschäft, als es ist — bei 20 % USt. um rund 20 Prozentpunkte. Der Mindestpreis wird dagegen **brutto** angezeigt, weil im Konfigurator ein Bruttopreis steht.
- **Externe IDs werden IMMER sofort nach dem Aufruf gespeichert**, vor allen Folgeschritten. WooCommerce-Produkt vor den Variationen, Printify-Produkt vor dem Publish, jedes Mockup einzeln vor der Zuweisung. API-Aufrufe lassen sich nicht zurückrollen; wird die ID erst am Ende gespeichert, bleibt nach einem Abbruch ein Objekt im Fremdsystem zurück, das die Toolsuite nicht kennt — und der nächste Versuch legt es doppelt an (bei Mockups: zahlt es doppelt).
- **`apply()` läuft nur unter `Cache::lock('schoolshop.provision.{id}')`** und liest den Antrag INNERHALB der Sperre neu. Ohne beides legt ein zweiter Klick während des minutenlangen Vorgangs alles ein zweites Mal an.
- **Zustandsfelder des CPT gehören ihren Aktionen.** `schuleFields($onboarding, includeState: true)` gibt es nur beim erstmaligen Anlegen. `bestellfenster_offen` und die Versandklassen-Marke werden danach ausschließlich von „Fenster öffnen/schließen" bzw. der On-Demand-Nachbearbeitung gesetzt — sonst nimmt ein erneutes „Shop anlegen" beides stumm zurück.
- **Die Namenssuche im Shop ist eine TEILSTRING-Suche.** „HAK Wien" trifft auch „HAK Wien 13". Jedes Ergebnis von `findProductsByName()` muss durch `productsByExactName()` laufen, das auf die Namen eingrenzt, die diese Schule haben kann. Ohne das werden fremde Schulen geschlossen.
- **PHP lehnt unmögliche Datumswerte nicht ab, es rechnet sie weiter.** `31.02.2026` wird zum 03.03., `04/16/2026` über `d/m/Y` zum 04.04.**2027**. `FluentFormsMapper::parseDate()` rechnet deshalb jedes Format zurück und verwirft es bei Abweichung. Die Rückfallebene `Carbon::parse()` gilt nur für Werte MIT Buchstaben — ein reiner Zahlenwert würde dort denselben Fehler wieder einführen.
- **Jede seitenweise Schleife braucht `assertPageLimit()`** (`ordersuite.woocommerce.max_pages`). Betroffen sind `fetchAllPages()`, `ensureAttributeTerms()` und `findProductsByCategory()`. Ohne Notbremse blättert die Schleife endlos weiter, sobald der Shop immer wieder volle Seiten liefert — genau so ist die Anwendung schon einmal ausgefallen.
- **Keine Seite wartet auf eine Schnittstelle.** Startseite (Fensterverlängerung), Antragsseite (Bestellzahlen) und Statistik holen alles über `app()->terminating()` nach der Antwort; angezeigt wird, was im Zwischenspeicher liegt. `RevenueReport::build()` bekommt aus dem Controller `allowFetching: false`. Nie zurückbauen — dieselbe Bauart hat die Anwendung zweimal lahmgelegt.
- **Das Sicherheitsnetz für Fehlerseiten darf keine HTTP-Status verschlucken.** In `bootstrap/app.php` sind alle `HttpExceptionInterface`-Fälle ausgenommen. Fehlt das, wird aus der Anmeldebremse (429), einer abgelaufenen Sitzung (419) und jedem `abort(409)` ein „unerwarteter technischer Fehler" mit Status 500.
- **Erstattungen werden gezählt, aber nie abgezogen.** Sie kommen ohne eigenen Abruf in der Bestellantwort mit (`refunds`) und stehen als Hinweis unter der Umsatzkachel. Abziehen ließe sich nur der Gesamtbetrag, nicht die betroffene Produktart — die Ranglisten würden dadurch falsch. Wer die Form der gespeicherten Monatsdaten ändert, muss die Kennung im Cache-Schlüssel (`statistics.orders.v2.…`) hochzählen, sonst zeigen bereits gespeicherte Monate das neue Feld dauerhaft leer.
- **Das Saisonziel ist ein gespeicherter Wert (`SeasonGoal`), kein Filter.** Es gilt je Schuljahr für alle im Team. Wer es zurück in die Adresszeile baut, macht aus einer Vereinbarung wieder eine private Ansicht — und die Kollegen sehen verschiedene Ziele. Dort stehen auch die Umsätze außerhalb des Shops: `manual_revenue` zählt zum Ist, `manual_forecast` nur in die Hochrechnung.
- **`StatisticsFilters::query($overrides)` legt die Übersteuerungen NACH LINKS.** Bei `+` gewinnt der linke Operand — stünden sie rechts, überschriebe der aktuelle Zustand jede Übersteuerung. Genau daran waren die Quellenschalter wirkungslos: Der Link zum Ausschalten trug kein `shop=0`, der zum Einschalten wurde es nicht mehr los. Ein ausdrückliches `null` im Override entfernt den Parameter und ist damit das „wieder einschalten".
- **`[hidden]` braucht `!important`.** Ein inline gesetztes `display` (`style="display:flex"`) schlägt die eingebaute Browserregel `[hidden]{display:none}` — ein per JavaScript verstecktes Element bleibt dann sichtbar. Die Regel steht im Layout; wer sie entfernt, bricht jede Anzeige, die mit `el.hidden` arbeitet.
- **Das Saisonziel darf nie aus einer gefilterten Zahl kommen.** Ohne eingetragenes Ziel gilt der Vorjahresumsatz — aber nur, wenn ALLE Quellenschalter an sind (`RevenueForecast::build(..., allSources:)`). Sonst wäre der Vorschlag nur der Ausschnitt der eingeschalteten Quelle: mit abgeschalteter Shop-Quelle 4.400 € statt 48.166 €. Ein Ziel ist eine Vereinbarung im Team und darf nicht davon abhängen, welche Schalter jemand gerade gesetzt hat.
- **Blade erkennt `@if` NICHT, wenn es direkt hinter einem Wortzeichen steht** (`gelaufen@if (…)`), weil das Direktiven-Muster ein `\B` davor verlangt — die Direktive landet dann wörtlich auf der Seite. Solche Fälle im `@php`-Block vorbereiten und mit `{{ }}` ausgeben.
- **Die Statistik zählt ein Bestellfenster JE ANTRAG, nicht je Kategorie.** „Folgejahr" legt regulär einen zweiten Antrag auf derselben Shop-Kategorie an. Wird wieder auf „ein Fenster je Kategorie" umgestellt, fehlt der Umsatz aller früheren Fenster derselben Schule im Durchschnitt.
- **www vs. ohne www:** `WC_STORE_URL` muss EXAKT die Endadresse sein. Bei 301-Redirect macht der HTTP-Client aus POST ein GET → Schreibzugriffe verschwinden still. Beide Write-Clients nutzen `allow_redirects=false` und brechen bei 3xx mit Klartext ab. Nicht „vereinfachen".
- **Pods REST-Rechte:** Der CPT „schule" braucht REST-Aktivierung am Pod UND Schreibrechte **pro Feld** (sonst werden Felder still ignoriert). `ShopProvisioner::verifySchuleFields()` liest zurück und meldet fehlende Felder.
- **Config-Cache:** Nach `.env`-Änderungen `php artisan config:cache` (bzw. neu deployen). Werte werden über `config('schoolshop.…')` gelesen, nie `env()` außerhalb von `config/`. Häufigste Ursache für „Webhook 404 trotz korrektem Secret": veralteter Config-Cache.
- **RunCloud Basic Auth blockt Server-to-Server:** Basic-Auth der Web-App wird VOR Laravel (nginx) erzwungen → externe POSTs (FluentForms) bekommen 401, bevor die App sie sieht. Lösung: FluentForms `Authorization: Basic <base64>`-Header, oder Basic Auth entfernen (Tool hat eigenes `TOOL_PASSWORD`).
- **PHP-Version-Pin:** `composer.json` hat `config.platform.php = 8.3.99`. Immer so lassen — sonst zieht `composer update` symfony-Pakete, die PHP ≥8.4.1 verlangen, und die CI (PHP 8.3) bricht beim Install.
- **On-Demand-Besonderheiten:** kein Bestellfenster/keine Klassenliste (Versand an Privatadresse) → im Konfigurator ausgeblendet, serverseitig erzwungen; Pods bekommt festes Fenster `2000-01-01`–`2099-01-01` (Konstanten in `SchoolOnboarding`).
- **Printify Marge:** Verkaufspreis ≥ (max. Variantenkosten + Versand) × (1 + `min_margin`, default 0,10). Vier Produkte (Jacke/Polo/Sportshirt/Match-Polo) haben nur Nicht-EU-Provider → längere Lieferzeit/Versand einkalkulieren.
- **Printify max. 100 Varianten:** Der Blueprint-Katalog hat oft hunderte Varianten (alle Farben × Größen). `PrintifyProvisioner::selectVariants()` filtert deshalb auf die im Konfigurator gewählten Farben/Größen (DE→EN über `printify.color_aliases`/`size_aliases`; erst exakt, dann Teilstring). Das ist **kein** Kosmetik-Filter — ohne ihn schlägt die API fehl und Printify erzeugt Vorschaubilder in nicht bestellten Farben. Passt nichts, wird bewusst abgebrochen (mit Liste der verfügbaren Werte) statt still alles anzulegen.
- **Printify-Versandprofile:** Ein Provider hat oft mehrere Profile. Ein Profil mit explizitem `AT` muss immer vor `REST_OF_THE_WORLD` gewählt werden (`PrintifyClient::shippingProfile()`), sonst stimmt der angezeigte Versandpreis nicht. Katalogdaten (Provider + Varianten + Versand) werden gemeinsam 24 h gecacht (`printify.catalog.{bp}.{pv}`).
- **Logo ist im Formular optional:** Viele Anträge kommen ohne Logo an. Alles, was ein Logo braucht (Printify, Mockups, Beitragsbild), muss `SchoolOnboarding::logoUrl($slot)` verwenden — nie direkt `logo_files[0]`.
- **Checkbox-Marker im Konfigurator:** Ein nicht angehaktes Kästchen wird nicht mitgeschickt. Die Druck-Häkchen (`print_front`/`print_back`) werden deshalb nur übernommen, wenn das versteckte Feld `print_slots_submitted` dabei ist — sonst würde jedes Speichern ohne den Logo-Bereich beide Drucke abschalten. Die Felder des Logo-Bereichs hängen per `form="configurator-form"` am Konfigurator-Formular (HTML erlaubt keine verschachtelten Formulare, die Upload-Formulare müssen eigenständig sein).
- **Webhook ist verlustsicher + protokolliert:** Jeder Treffer wird in `webhook_logs` gespeichert (sichtbar unter Schul-Onboarding), bevor irgendeine Logik läuft. Schlägt das Mapping fehl, wird der Rohdatensatz trotzdem als Antrag gesichert. GET auf die Webhook-URL = Browser-Test (200/404/503).
- **Toolsuite verschickt NIE selbst E-Mails.** Kein Mailer/SMTP in Laravel konfiguriert (bewusst so lassen). Ausfall-Alarme laufen über `WordPressAdminNotifier` → POST an einen custom WP-REST-Endpunkt (`wordpress-mu-plugin/weartogether-notify.php`, muss auf dem WP-Server als mu-Plugin liegen), der dort `wp_mail()` aufruft. Fehlt das mu-Plugin, schlägt der Call einfach fehl (404) — kein Absturz, nur kein Alarm.
- **Status sind keine Etiketten:** `angelegt`/`abgeschlossen` dürfen nur durch die tatsächliche Aktion entstehen (`ShopProvisioner::apply()` bzw. `closeOrderWindow()`). Neue Statuswerte immer in `OnboardingStatus` beschreiben UND in `manualOptions()`/`actionOnly()` einsortieren, sonst lässt sich im Konfigurator etwas behaupten, das im Shop fehlt.
- **Startseite darf nie an einer API hängen:** `Dashboard` liest ausschließlich die eigene Datenbank. Die Fensterverlängerung dort läuft über `runDueOpportunistically()` — gedrosselt, in try/catch, Fehler nur ins Log.
- **Präsentationsblatt — drei Ebenen:** Fotos zuerst, darüber der Hintergrund (`resources/presentation-sheet/background.png`, PNG mit transparenten Fenstern), darüber Texte/Icons/QR. Der Hintergrund übernimmt das Freistellen der schrägen Rahmen und des Kreises — deshalb **kein** Polygon-Masking im Code. Die Detailaufnahme muss trotzdem rund maskiert werden, sonst überdeckt ihr Quadrat das darunterliegende Mockup (beide liegen unter dem Hintergrund).
- **Blade: `@php(...)` und `@php … @endphp` nie in derselben Datei mischen.** Blades Regex für den Blockform-`@php` greift vom ersten inline `@php(` bis zum nächsten `@endphp` und verschluckt alles dazwischen — die Vorlage kompiliert dann still falsch. Gilt auch für ein `@php(` in einem Blade-Kommentar.
- **dompdf setzt Text tiefer als angefragt** (`factor × Schriftgröße − offset`, gemessen in `presentation_sheet.text_top_correction`). Die `top`-Werte in der Config sind Buchstaben-Oberkanten wie in InDesign; `PresentationSheetTest` rechnet zurück und prüft gegen die Vorlagenkoordinaten.
- **dompdf liest nur innerhalb des Projektverzeichnisses** (chroot). Erzeugte Bilder müssen deshalb unter `storage/app/public` liegen, nicht in `/tmp`.
- **`fetchAllPages()` braucht die Notbremse (`ordersuite.woocommerce.max_pages`):** Ohne sie blättert die Schleife endlos weiter, sobald der Shop `X-WP-TotalPages` nicht mitschickt (Caching-Plugin, Proxy) und jede Seite voll ist. Der PHP-Prozess hängt dann für immer; nach ein paar Aufrufen ist keine FPM-Arbeitskraft mehr frei und die **ganze Anwendung** antwortet nicht mehr. Genau das ist beim ersten Aufruf der Statistik passiert.
- **Die Statistik-Seite ruft den Shop NIE synchron auf.** `StatisticsController` prüft nur `StatisticsWarmer::progress()` (reine Cache-Abfrage) und zeigt entweder die fertige Auswertung oder `statistics/loading.blade.php`. Der Abruf läuft ausschließlich über `app()->terminating()` — also **nach** der Antwort, mit `ignore_user_abort`, damit er weiterläuft, wenn jemand die Seite verlässt. Nie zurückbauen auf „Seite holt selbst": genau das hat die Anwendung schon einmal lahmgelegt.
- **Halbe Zahlen sind schlimmer als keine.** Solange nicht alle Monate da sind, zeigt die Seite ausschließlich Fortschrittsbalken und Spinner — keine Kennzahl, kein Diagramm.
- **Nur ein Aufbau-Durchgang gleichzeitig** (`Cache::lock('statistics.warm.lock')`) und `statistics.pause_ms` zwischen zwei Shop-Anfragen. Der Webshop läuft auf demselben Server und darf durch die Auswertung nicht ausgebremst werden — die Pause ist Absicht, keine Bremse zum Wegoptimieren.
- **Statistik lädt monatsweise und cacht je Monat** (`OrderRepository`). Nie auf „ein Abruf pro Schuljahr" zurückbauen: ein Jahr sind tausende Bestellungen, ein einziger Abruf läuft minutenlang und speichert bei Abbruch nichts — jeder Versuch begänne wieder bei null.
- **Monatsgrenzen sind ausschließend:** WooCommerce behandelt `after`/`before` exklusiv. Deshalb `after` = letzte Sekunde des Vormonats, `before` = erster Augenblick des Folgemonats — sonst fällt eine Bestellung, die exakt um Mitternacht des Monatsersten eingeht, in jedem Monat durchs Raster. `StatisticsTest` prüft den Fall.
- **Ein `Http::fake()`, der `after`/`before` ignoriert, verdeckt genau diese Fehler.** Der Fake in `StatisticsTest` filtert deshalb echt nach Zeitraum — vorher zählte er beim monatsweisen Abruf jede Bestellung zwölfmal.
- **Die Schulen der Statistik kommen aus den SHOP-KATEGORIEN, nicht aus den Onboarding-Anträgen.** Die Toolsuite kennt nur, was sie selbst angelegt hat; alles ältere fehlte sonst komplett — genau daran waren „Ø je Bestellfenster" (0 €) und die Fensterliste (zu kurz) gescheitert. `RevenueReport::schools()` nimmt jede Kategorie unter `schoolshop.parent_category_name` und hängt den passenden Antrag an (über `woo_category_id`, hilfsweise über den Namen). Der Antrag liefert nur noch Lieferart und Fensterdaten; Umsatz und Ranglisten brauchen ihn nicht.
- **Statistik-Fensterpuffer ist Absicht, kein Schätzfehler:** Der Auswertungszeitraum je Sammelbestellfenster ist breiter als im Antrag eingestellt (Standard 7 Tage davor, 21 danach, in der Filterzeile änderbar). Grund: die automatische Nachfrist verlängert oft um eine Woche, und Nachzügler bestellen auch danach. Da nie zwei Fenster derselben Schule aneinander liegen, kann der Puffer keine fremden Bestellungen einsammeln. Auf der Seite per ⓘ erklärt — beim Ändern der Defaults den Erklärtext mitziehen.
- **Diagramm-Farben sind geprüft, nicht gewählt:** Blau `#2a78d6` / Orange `#eb6834` (`Charts\Palette`) sind gegen Farbsehschwäche validiert (ΔE 24,7 protan auf weißem Grund, Zielwert ≥ 8) und liegen über 3:1 Kontrast. Wer sie ändert, muss neu prüfen. Jedes Diagramm hat zusätzlich Legende **und** Tabellenansicht, damit Farbe nie der einzige Informationsträger ist. Beschriftungen tragen immer Textfarben (`.chart-tick`/`.chart-value`), nie die Serienfarbe.
- **Diagramme schrumpfen auf dem Telefon nicht mit**, sondern scrollen waagrecht im eigenen Kasten (`.chart-scroll` + `min-width` am SVG) — bei 390 px wäre die Beschriftung sonst 6 px groß. Die Seite selbst darf nie waagrecht scrollen.
- **Einfaches Anführungszeichen in `label="…"`/`title="…"` bricht die Seite:** das Attribut endet dort vorzeitig, Blade erkennt die Komponente nicht mehr und die Vorlage wirft einen Syntaxfehler („unexpected endif"). In deutschen Texten gehören ohnehin `„` und `“` hinein; `HelpUiTest` prüft das.
- **`Http::fake()` in Tests überschreibt eine bereits registrierte URL NICHT** (erste Registrierung gewinnt) — für Tests, die denselben Endpunkt über mehrere Aufrufe hinweg unterschiedlich antworten lassen müssen (z. B. Status-Wechsel OK→Fehler→OK), `Http::fake(['url' => Http::sequence()->push(...)->push(...)])` verwenden, nicht `Http::fake()` mehrfach mit derselben URL aufrufen.

## Deployment & Versionsnummer
- RunCloud Git Atomic Deployment vom Branch; Deploy-Script macht `composer install --no-dev`, `config:cache`, `route:cache`, `view:cache`, `migrate --force`. `.env` und `storage` sind persistente Symlinks.
- **Versionsnummer:** Datei `VERSION` (eine Ganzzahl), angezeigt in der Navbar als „v{N}". **Regel: bei JEDEM Push die Zahl um 1 erhöhen** — so sieht der Nutzer auf der Live-Seite, ob der Push schon deployt wurde.

## Konventionen
- Vor jedem Push `php artisan test` grün halten; neue Funktionen bekommen einen Feature-Test.
- Fehler nie als kahler 500er: erklärte Meldung + kopierbare technische Details (`errors/friendly.blade.php`, `WooCommerceApiException`, Session-`provisionError`).
- Entwicklung/Push auf Branch `claude/python-modernization-spec-cqxq2g`. Commit-/PR-Texte ohne Modell-Identifier.
- Deutschsprachige UI-Texte und Kommentare (bestehendem Stil folgen).
